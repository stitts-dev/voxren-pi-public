# Loops

Three loops keep this repository moving while the player tests the coach: a captain loop that takes issues to merged pull requests, a dev loop that keeps the integration worktree and the player's coach current, and a QA loop that scores every change to dev and files what regressed. They run on two machines in three different sessions. This file is their one contract: each loop's prompt (a routine, a session cron job, or a person typing "go next") is a pointer to a section here, plus the values that are that machine's own (paths, the gate script, the session title). To change a loop, change this file in a pull request; the next tick reads it from `origin/main`.

AGENTS.md "Working alongside other sessions" wins when the two differ.

## Shared definitions

Every loop uses these words the same way.

- **dev.** `just dev` (`src/lab/dev-rebuild.sh`): `origin/main` plus every open pull request that merges cleanly, lowest number first, drafts included, checks pending or not; a pull request that conflicts is left out and its line says whether it conflicts with main (its session rebases) or with a pull request already in (it waits for that one). Each machine has its own dev worktree built by this one recipe: the Windows one runs the player's coach, the Mac one is the merge gate. `just dev --worktree qa` builds the QA loop's copy the same way. `DEV_SKIP` holds the pull requests a machine leaves out, and the loop's report says which.
- **green.** `npm run typecheck` exit 0 and `bun test` exit 0 on that dev tree, each run bare with its output written to a file (`.claude/guards/suite-pipe.mjs` refuses a test run piped through `head` or `tail`). A failure that also happens on unmodified `origin/main` is main's, not the pull request's.
- **a claim.** An issue is taken when any of these holds: the label `in-wave` is on it and its newest `wave:` comment (`wave: <machine> <session> <ISO time>`) is under 3 hours old; an open pull request references it; a remote branch names its number. A captain checks all three before taking an issue, and clears a stale `in-wave` label (over 3 hours, no pull request) before taking it. The label is the only claim the other machine can see.
- **decisions.** One place: the decision log, issue #475, one comment per decision, `D<n> | question | choice | why | by | date | links`, written by a captain and nobody else. A row whose choice is "pending owner" is the owner's open question. Every loop reports the owner's open questions by reading #475, never from its own notes, and none asks the owner anything a #475 row does not already hold.
- **merging** (AGENTS.md rule 6). A pull request is merged by the captain that proved it, whoever opened it: it is in a dev build that is green, its diff was read, it is not a draft, and neither it nor its issue carries `needs-owner`. Squash, delete the branch, confirm with `gh pr view <n> --json state`, close the issue by hand when the body lacks "Closes". A loop that cannot merge (its permission classifier refuses `gh pr merge`) lists the pull request as "ready, the captain merges on its next pass"; it does not ask the owner to merge.
- **titles.** A loop session is named `WORKING · <topic>` while it works, `DONE · <what shipped>` when it ends with nothing owed, `NEEDS YOU · <one line>` only when a `needs-owner` row in #475 blocks the rest. A tick with nothing to do keeps its name and ends in one line.
- **a report** opens with the four lines of AGENTS.md "Working alongside other sessions" 5, then the board (`ListAgents`: every running session and the loop's own background work), then what was merged, what failed and why, the #475 rows written, and the owner's open rows.
- **forbidden in every loop.** Paid runs: `just stories`, `just smoke record`, `coach`, `pi`, `claude -p`, any lab that calls a model. Editing `~/.claude/settings.json`. Pushing `dev`. Force-pushing. Merging on a red or pending dev suite. Deleting a worktree or branch that is not the loop's own and merged. `cmd; echo $?` and a test run piped through `head` or `tail` (hooks refuse both). The shell on the Mac is zsh: flags and paths written out in full, multi-step scripts in `bash -euo pipefail -c '...'`.

## Captain loop

Who: the Mac routine "voxren-pi captain relay" (hourly, a fresh session each run), and the Windows session the owner drives with "go next". Both follow these steps; a parameter is in angle brackets.

1. **Is there work?** Read `~/.claude/handoffs/captain.lock` on this machine (`<ISO time> <session id> <issues>`): it holds while under 3 hours old and one of its issues is still open with no merged pull request; a stale lock is deleted. List sessions (`mcp__ccd_session_mgmt__list_sessions`, or `ListAgents`): a session titled `WORKING ·` with activity under 3 hours old is a captain at work. Either way, print "relay: captain busy (<what>)" and stop. One captain per machine; the other machine's captain shows through the claims below, not through this lock.
2. **Sweep.** When an open pull request is not a draft and carries no `needs-owner`: `just dev` (on "dependencies changed", `npm run setup:worktree` in dev first), run the typecheck and the suite in dev (see green), read each such pull request's diff, and merge every one the green dev proves (see merging). A red dev: find which pull request breaks it by running the failing file on `origin/main` plus each pull request in number order, comment on that pull request with the failing lines, and merge the rest if dev without it is green. This is how a pull request opened by a session that cannot merge gets in.
3. **Pick the batch** (read-only). Candidates: open issues labelled `bug`, `regression`, or `ready-for-agent`. Drop any that is claimed (see a claim), labelled `needs-owner`, `needs-info`, `ready-for-human`, `needs-windows`, or `wayfinder:*`, or that a "pending owner" row in #475 names. Order: `regression`, then `bug`, then `ready-for-agent`, lowest number first; take up to 3, and keep a series that depends on itself in one batch. Nothing left: go to triage.
4. **Triage** (only when no batch was found). Up to 5 open issues with no label or only `needs-triage`, oldest first, not `wayfinder:*`, `ready-for-human`, or #475. Read each with its comments, check its claim against `origin/main` (`git grep`, `git show origin/main:<path>`), then label it exactly once: `ready-for-agent` (small, clear, code only), `needs-owner` (a decision, a secret, a paid run), `needs-windows` (the Windows screen or a clean Windows machine), `needs-info` (the claim does not hold or is unclear), with a one-line comment saying why. Print "relay: triaged <n> issues (<labels>)" and stop.
5. **Claim.** For each issue in the batch: `gh issue edit <n> --add-label in-wave` and `gh issue comment <n> --body "wave: <machine> <session id> <ISO time>"`. Write the lock. Set the title to `WORKING · ship-wave #a #b #c`. Read the newest handoff in `~/.claude/handoffs/`, AGENTS.md rules 6 to 8, and #475.
6. **Ship.** `Workflow({name: 'ship-wave', args: {issues: [a, b, c], decisionLog: 475}})`. It returns `{approved, failed, decisions_needed}` and never merges or posts.
7. **Merge what passes.** The sweep of step 2 again, now with the wave's approved pull requests in dev: `just dev`, the gate, each diff read, every pull request the green dev proves merged. A pull request a wave rejected, or that needs the owner, a paid run, or the Windows screen: a comment on its issue saying why, the label `needs-owner` or `needs-windows`, and a row in #475.
8. **Close out.** Remove `in-wave` from each issue of the batch (merged or not). Post the #475 rows. Fast-forward the primary checkout (`git merge --ff-only origin/main`; never over local edits). Run `just dev` once more so the player's next coach start has the merged tree. Run the team-player audit when this machine has it (`node <team-player checkout>/audit/run.ts --project <project slug> --since 3`) and keep the rows for this batch. Write `~/.claude/handoffs/<session id>.md` (goal, merged, failed, decisions, audit rows, next). Delete the lock. Title `DONE · ship-wave #a #b #c: <n> merged`, or `NEEDS YOU · <one line>` when a `needs-owner` row blocks the rest. Remove only this captain's own clean, merged worktrees.

The Windows captain adds one step: before the batch, it runs `git fetch` so its view of `origin/main` and the remote branches is current, and it leaves merging to the machine whose classifier allows it when its own refuses (see merging).

## Dev loop

Who: the Windows session "Agent task monitor plugin", woken by its gate (a background shell that exits when main, the open pull requests' heads, the dev worktree, or session activity change; an hourly safety tick re-arms it). One tick, two parts, then one line.

1. **Dev.** `just dev`. On "dependencies changed", `npm run setup:worktree` in dev first. On "rebuilt", start the suite on the result in the background (`just devbox` from dev, output to a file, exit code kept) and report pass or fail when it ends; "no change" and "same content" owe no suite. A pull request LEFT OUT for a conflict with main: poke its session once with the file names. One that conflicts only with another pull request: say so, no poke.
2. **Threads.** List today's sessions and sort each, acting once per change of state. (a) Not active with work left (idle, and it has a failed check, an unverified step it named, review findings not handled, uncommitted or unpushed work, or a conflict with main): one short message, its state in one line, then "continue with your next step that is local and reversible, or say the one decision you need"; no second poke until it shows new activity. (b) Finished (its pull request merged, or nothing left): tell it once to clean up what is its own and say what it removed; title `DONE · <what shipped>`. (c) Waiting on the owner only: no message; title `NEEDS YOU · <one word> · <topic>` only when a #475 row says so. A working thread gets nothing.
3. **One line.** What changed (dev, suite result, threads touched), the pull requests that are green in dev and wait for the captain, and the owner's open rows from #475. Nothing changed: "pass N, HH:MMZ: no change".

The dev loop never merges, never opens a pull request for another session's branch unless that session has been idle for over 3 hours with a finished commit (then it says so in the pull request body), never relays a go-ahead, and never asks the owner to merge.

## QA loop

Who: the Mac routine "voxren-pi QA loop" (hourly, after the captain's slot, a fresh session each run). It scores dev and files what regressed; it never fixes.

1. **Build.** `just dev --worktree qa`. On "dependencies changed" (or a fresh worktree), `npm run setup:worktree` there. On "no change" or "same content", when that worktree already has a `.claude/conductor/scores.json`: print "qa: no change (<sha>)" and stop. A worktree with no scores yet is scored once whatever the build said.
2. **Score.** `node <team-player checkout>/conductor/cli.ts score quick --repo <qa worktree>`. It runs `just score` there (typecheck, `bun test`, the UI catalogue tier from `just ui`, and every other `tier.json` under `.claude/conductor/tiers/`), compares with the previous `.claude/conductor/scores.json` in that worktree (`scoreDelta`: a tier whose failures rose, a metric past its tolerance), writes the new one, and prints the delta and each tier's findings. The paid tier (`just score --stories`) is never run here; the report says how old the last full score is.
3. **Bisect a regression.** For each failing test file: run it alone on `origin/main` (`git -C <qa> reset --hard origin/main`, then `bun test <file>`); then on main plus each open pull request in number order (`git merge` one at a time, the file after each). The first tree that fails names the culprit: a pull request, or main itself. Rebuild with `just dev --worktree qa` when done.
4. **File it.** One issue per failing test, labelled `regression` and `bug`, titled `regression: <test name>`, body: the failing lines, the dev tree, the culprit (pull request or main commit), and the fingerprint line `<!-- qa:fp=<test file>:<test name> -->`. Search open issues for the fingerprint first; a second sighting is a comment, not a second issue. A culprit pull request gets one comment naming the issue. A culprit on main is a red main (AGENTS.md rule 6): the comment goes on the pull request that merged it. A UI-tier finding is filed the same way with its `key` as the fingerprint. At most 3 new issues per run.
5. **One line.** The dev tree, each tier as `pass/fail`, the delta, the issues filed or commented, and the age of the last full score. Nothing regressed: "qa: <sha> green (<unit> unit, <ui> ui), no change".

The captain loop takes `regression` issues before anything else, so a regression found at :55 is in a wave at :25.

## Keeping the three in sync

- A loop prompt is a pointer: "Follow docs/loops.md on origin/main, section <name>, with <machine values>". The prompt names the machine's paths, the gate script, and the team-player checkout; nothing else lives in it.
- A change to any loop is a pull request to this file. The routines read `origin/main` each run, so a merged change is live on the next tick; a Windows session cron job is re-armed by its owner with the same one-line pointer.
- A loop that finds this file and its prompt disagreeing follows this file and says so in its one line.
