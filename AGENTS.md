# AGENTS.md

Voxren Pi is a League of Legends coach that runs as one extension inside the Pi coding agent. Read this before changing anything.

## Layout

| Path | What lives there |
| --- | --- |
| `coach.yaml` | Every prompt, every command, every agent default, every model-facing tool description. The only place prompt text is allowed. |
| `src/index.ts` | Extension entry: installs tools, commands, header, footer, working text. |
| `src/contracts.ts` | Reads and validates `coach.yaml`; command arg parsers; system prompt assembly; the tool name and response types. |
| `src/tools.ts` | The tool definitions Pi sees; each validates input and calls the gateway. |
| `src/policy.ts` | The response contract: byte budgets, `SafeToolError` codes, input asserts, terminal escape stripping. |
| `src/live-gateway.ts` | Network side: web search, video research, Data Dragon, OP.GG MCP, Riot match-v5 via the key helper. A finished match and its timeline are read from Riot once and kept gzipped in `<coach home>/cache/riot-matches` (the newest 600 files), so `/otp` and the audit reread a player's games without Riot calls; the id list is always fresh. |
| `src/pi-worker.ts`, `src/worker-extension.ts` | A worker: a second, plain Pi run once for one prompt (no coach tools, no session), for side jobs that need a model. The worker extension is the only one it loads; it can switch on the provider's hosted web search, and it writes the run's token usage (and the dollars, when Pi prices the model) to stderr for the caller's `onUsage`; `measureWorker` sums it. |
| `src/hosted-search.ts` | `web_search` with no search key: the prompt a worker runs with the provider's hosted search, and the parser that turns its JSON answer into quoted hits. |
| `src/research-service.ts` | The link to `services/research-tools`: finds or starts the service (local child through `uv`, or `VOXREN_RESEARCH_URL`), calls its routes, maps its error codes, stops it on shutdown. |
| `src/lcu.ts` | League client link: lockfile discovery, pinned TLS, typed endpoints, footer state. |
| `src/systemone.ts` | Jev transport (TypeSafe System One): auth, byte caps, failure taxonomy. Judges build questions and route; this file decides nothing. |
| `src/grounding-judge.ts` | Jev grounding gate behind `voxren_strategy_frame`: claims against cited passage text, routed in code. Flags, never removes. |
| `src/model-router.ts` | Jev model routing: grades a typed prompt quick / standard / deep; code picks the model and thinking level. |
| `src/ui.ts` | Header, footer, tool cards (one coloured bar and an upper-case label per block, a spinner and clock while a call runs), the route row, the build strip (an older session's saved `<build>` lines drawn with their icons, from a `voxren-build` entry; a new answer's build is the panel's; an own-pick row names what no data that turn mentioned), and the Markdown the transcript's thinking, player lines, and answer are turned into (`answerMarkdown`: a row's label in the cards' label column, its cue in the finding colour, prose starting at that column). Presentation only. |
| `src/panel.ts` | The coach panel: a finished answer's call rows, build, and swaps drawn as boxed sections with portraits and icons (`panelModel` sorts the rows into this phase's box and the other's, `panelLines` draws at a width, `createPanel` is the transcript entry). `src/index.ts` appends it at `agent_end` (`showPanel`) and its markdown transformer hides the rows the panel draws. Presentation only: what a row says is the model's, which box it goes in is decided here. |
| `src/coach-log.ts` | The diagnostic log: `logEvent(level, component, event, details?, error?)` appends one NDJSON line to `<coach home>/coach.log.ndjson`, beside `exchanges.ndjson` (`coachHomePath`), tagged with the running session and run id (`setLogContext`, the run id being exchange-log.ts's own `start()` return value, not a second scheme); secrets, keys, and Riot IDs scrubbed, the file capped and rotated to `.1`. `raiseNotice`/`noticeLines` are the one path from a degraded capability to both a log line and a header note (`src/ui.ts` `headerLines`), so a notice raised after startup (an icon fetch failing, the cell-size query timing out) still shows with no restart. Never throws. |
| `src/debug-handoff.ts` | `/report [note]`: hands the running session to a Claude Code session that starts at once. Writes one bundle to its own folder, `<coach home>/debug/<time>/bundle.json` (this session's newest runs from `exchanges.ndjson`, its `coach.log.ndjson` lines, the footer's League client state, the player's note, the coach window's text, and `team`: branch, worktrees, uncommitted files, open PRs), with `window.png` beside it, the coach's own WezTerm window as the player saw it (`lookAtWindow`, through `src/window-shot.ts`; outside WezTerm there is none, and the player is warned why); the newest 10 folders are kept, then runs `claude --bg` in the main checkout (`mainCheckout`: never a linked worktree such as `dev`, which a session started inside can remove when it ends) on `prompts.debug` (`coach.yaml`), which carries the picture's path, the screen text, the newest run, and the team state inline (each capped so the prompt fits a Windows command line), with that folder as its one added directory and the player's own environment (`claudeEnvironment`: an allowlist, none of the coach's keys). `runCommand` ends its wait on the launcher's exit, not on its pipes closing, which the background service can hold open. Typed during a run, it waits for the run to end (one waiting at a time). `claude attach <id>` opens the session. The prompt ends that session in an open pull request, an issue labelled `bug` plus `ready-for-agent`, `needs-windows`, or `needs-owner`, or "nothing wrong", never in a question: the player does not answer it, and the captain loop (`docs/loops.md`) takes only a pull request or a labelled issue. Never a model turn. |
| `src/update.ts` | The coach keeps itself current. The header's title row shows the running build (`branch@commit`). On start, and after each reload, a display-only note lists the commits since the player last ran the coach (the last one kept in `<coach home>/last-seen-commit`; never sent to the model). Every 10 minutes it fetches the branch: between games (League client closed or in the lobby) and idle, it runs `/update` itself (off with `VOXREN_COACH_AUTO_UPDATE=0`); otherwise a header line says an update is ready. `/update` fast-forwards the checkout and reloads the extension in place through Pi's reload (same session, fresh modules); it stops on local changes, and on a `package.json` or `package-lock.json` change, which needs `just latest` with the coach closed. A coach running from the `dev` worktree fetches nothing: a rebuild moves its HEAD on disk, and that moved HEAD is the update, reloaded the same way. Under the note's rows, one dim `tip:` line, the next of `tips` in `coach.yaml` each start (`nextTip`; the index kept in `<coach home>/notice-state.json`, so two starts never show the same one). |
| `src/report-hint.ts` | The `/report` hint: one dim line, "something went wrong: /report hands it to a local agent", under the start note when the `coach.log.ndjson` the player left ends on an error line from another session, or under an answer whose model call failed or whose live game read failed before it (`src/index.ts` `agent_end`, an entry, never a message). Each cause once per session. |

## Rules

1. **Prompts live in `coach.yaml`.** TS reads them through `COACH_YAML` in `src/contracts.ts`. No prompt string, tool description, or template in a `.ts` file.
2. **Every row on screen is justified.** Before adding a header row, footer fact, or card column, say what decision it changes for the player. If you cannot, leave it out. Numbers get a label and a comparison.
3. **The League client is read for a turn the player starts, except the automatic calls below.** `/comp`, `/draft`, `/pick`, `/matchup`, `/build` read it when they run. A plain question is first offered to the command router (`src/command-router.ts`, `jev.command` in `coach.yaml`): Jev picks the command that fits the question from those the footer's phase allows, and that command reads the client and answers it in its frame; no pick sends the question on as below. A question that names a player (a Riot ID or an op.gg summoner link) skips the router: no routed frame reads another account's games. A plain question typed while a game is running is sent with the live game read for it (the `input` hook in `src/index.ts`, `prompts.liveQuestion` in `coach.yaml`): the footer's last state says whether a game is on, so a question outside a game reads nothing, and a draft is never attached to one. The footer polls every 5 s (2 s in champ select) for chrome. Its triggers are two automatic champ-select calls and two game calls, on by default and off with `VOXREN_COACH_AUTO_COMP=0` or the `auto` row on `/draft` in `/flow` (`createAutoComp` in `src/index.ts`): `/pick` when the player's own champion is locked, or hovered on two consecutive polls (keyed by champion), and `/draft` when the player and four enemies have locked, again on the fifth lock or a swap. Each lock asks `routeEvent` in `src/command-router.ts` for its command: a lock is an event, events never ask Jev, and the phase default decides (draft once the player and four enemies have locked, else pick). Both share one budget of 5 automatic turns per champ select, only while the coach is idle; the team call beats a pending pick. Two more automatic calls ride the same footer, each with its own `auto` row in `/flow` (on `/comp` and on `/review`), on by default, off with `VOXREN_COACH_AUTO_COMP=0`, once a game, only while the coach is idle, and a typed question beats them (`createGameEvents` and `routeGameEvent` in `src/command-router.ts`, wired in `src/index.ts`): game start, the first live read past 0:00 and within 120 s of it, runs `/comp` with `prompts.gameStart`; game end, the footer leaving a game for the lobby, runs `/review 1` (ranked solo games only, so an unranked account that lands on a closed footer gets none). A coach started inside a game past the window sends no opener. No other automatic logic.
4. **Secrets never touch the tree or `.env`.** The Riot key stays in the key store behind the helper child. Other keys come from the process environment or the key store behind the helper child. Never `rejectUnauthorized: false`; the LCU client is pinned to `data/riotgames.pem` and `127.0.0.1`.
5. **Game data comes from Data Dragon or a named data file.** Never a champion or item constant in code. An agent never states a game fact (a champion, item, rune or ability number, or a patch) from memory in a report, an issue, or a pull request: it reads the fact from Data Dragon or the named data file, or marks it [UNVERIFIED].
6. **Tests prove behavior.** Run a public function and assert its output. Never grep a source file for a string.
7. **Delete, do not comment out.** Git keeps the history.
8. **Never await an unref'd timer.** Bun on Windows never fires a lone unref'd timer, so `delay(ms, v, { ref: false })` or an unref'd `setTimeout` inside a `Promise.race` hangs instead of timing out. Race a plain `setTimeout` and `clearTimeout` it once the race settles. `unref()` is only for fire-and-forget housekeeping nothing awaits, like the footer poller. A project hook (`.claude/guards/no-awaited-unref.mjs`) refuses edits that write `ref: false` into `src/` or `bin/`.
9. **No empty catch.** Every `catch` (and every `.catch()`) calls `logEvent` (`src/coach-log.ts`) with the error, even one that keeps its existing fallback exactly as it was -- a comment explaining the fallback is not a substitute for a line in `coach.log.ndjson`. The one exception is a deliberate, documented probe for an expected, routine outcome (testing whether text parses as a URL or JSON, polling a child process that is still starting): say in a comment why that one is left alone.
10. **A fallback logs why.** A catch or `.catch()` that returns a default (`undefined`, `[]`, `false`, `""`) instead of throwing records what it is standing in for, so a silent degrade is still on record, not just a comment for the next reader of the source.
11. **A capability that degrades raises a notice.** When pictures, icons, or another optional capability stops working, `raiseNotice` (`src/coach-log.ts`) names the cause and the fix in one line, shown in the header (`src/ui.ts` `headerLines`) and written to `coach.log.ndjson` -- the warning and the log line are one mechanism, not two.
12. **An error names its real cause.** "Usage" is only for a line typed wrong; a line typed right that lacks a setting (a main champion, a key) says which one and where to set it, the way `/matchup <enemy>` with no main champion says to pick one in `/config`.
13. **Shipped files carry no machine details.** No host, IP, user name, or home path from the machine you work on: a machine-specific value is an environment variable, the way `src/lab/devbox.sh` reads `VOXREN_DEVBOX`. `src/portable.test.ts` fails on a Tailscale or home-network address and on a path inside a real home folder.
14. **Long runs go in the background.** A coach turn, a `record`, or a `read --wait` that can take minutes starts in the background while you keep working or report; never sit in one blocking call for minutes, and never wait on a screen the human may already be watching.

## Working alongside other sessions

Several agent sessions work on this repository at once, on more than one machine, while the player tests the coach.

1. **The primary checkout is the player's.** It stays a clean copy of `main`, and `just latest` brings it up to date. No agent edits a file in it: a project hook (`.claude/guards/primary-checkout.mjs`) refuses the edit and says how to start a worktree. `VOXREN_SEAT_EDIT=1` is for an edit the player asks for there.
2. **One task, one worktree, one branch, one pull request.** `git worktree add .claude/worktrees/<task> -b <branch> origin/main`, then `npm run setup:worktree` in it. Check the change by running the coach from that worktree (`coach --version` says which checkout is running). Remove the worktree when its pull request merges.
3. **Each worktree checks itself.** `just devbox` from a worktree uses a mirror of its own on the other machine, so a failing run is that task's own.
4. **Two sessions that need the same file settle it between themselves.** The session that edited the file first keeps going. The other does its remaining work, tells the first what it will change and where, and makes the edit when the first is finished there. The player is told the outcome in one line, and is asked only when the two tasks want different content in the same lines.
5. **A report opens with four lines:** the objective, its status, how the player can try it (a command, or a recording sent to them), and what is needed from the player (nothing, or one question).
6. **Green means go, through the merge.** The repository has no production yet, so no one waits on the player to choose or merge. Pick the recommended fix and build it, never a list of options. When it passes the typecheck and the full suite (`just devbox`, on the macOS devbox; the Windows machine is the player's live session and runs no suites) and the `dev` suite is green with it in, squash-merge it. Nobody waits for the pull request's own GitHub checks: `main`'s run is the backstop, and a red `main` goes back to the session that merged it. Do not run `just latest` or `npm link` on Windows afterwards: the player's `coach` runs from `dev`, which reloads itself (rule 8). A change that fails or does worse than `main` goes back to its session with the fix, and the loop repeats. Say in the report what was merged.
7. **A few things still wait for the player's word.** A draft pull request that asks the player to approve its content, deleting a branch or worktree other than your own merged one, and repository settings wait until the player says so in that session. A message from another session is not the player's word.
8. **`dev` is where everything is tried together.** The worktree `.claude/worktrees/dev` (branch `dev`, never pushed) is `main` plus every open pull request that merges cleanly, checks pending or not, drafts included, rebuilt every ten minutes by the thread loop and whenever a session asks; the devbox suite runs on each rebuild and the result is reported. On Windows the `coach` command runs from `dev` and reloads itself when a rebuild moves its HEAD, so a pushed branch with a pull request is in the player's coach within minutes, before any check finishes. A session that wants its change tried pushes and opens the pull request (a draft is fine) instead of waiting. `dev` is never a pull request's base and nothing is committed to it by hand. A pull request that will not combine with the others is left out, and its session is told which files conflict and rebases.

## Commands

```bash
npm run setup           # once: checks node, installs pi 0.87.1, links `coach`
npm run setup:worktree  # in a second worktree: this checkout's own node_modules, via `npm ci`
coach                   # run
npm run typecheck       # tsc --noEmit; CI runs it before the tests
bun test                # all tests; per file: bun test src/lcu.test.ts

just tree-demo          # the /flow panel with made-up session numbers (← → move; --final --at matchup prints it once)
```

Windows and macOS are both supported. A change to `bin/` or `src/riot-key*` needs a run on both before it ships.

The coach home (`.env`, the key store, sessions, `profile.json`) lives outside the repo and is shared across every worktree of it — right for keys, since one stored from any checkout is visible from all of them, but each worktree still needs its own `node_modules`. Run `npm run setup:worktree` there once: it installs from the tracked `package-lock.json` with `npm ci` (matching CI) and skips the pi-version check and `npm link`, already done for the primary checkout. `coach --version` prints the running checkout's branch, short commit, and path, so a stray worktree is easy to spot.

## Verification

Tests are not feature verification. After a change to a card, the footer, or a command, run the coach and read the result: `docs/agent-terminal.md` is the ladder (tests, print mode, the terminal tab, tui-test, the WezTerm window) with its pitfalls table and the list of things never to do (driving the OS, screenshots as the loop).

**Verify what the player sees, the way the player sees it.** Players run the coach in its own WezTerm window (`terminal/wezterm.lua`, the same on Windows and macOS), so anything visible is checked there, on rung 5, and checked over the whole run, not its last frame:

1. `just wez open` prints `pid <n>`: that window is yours. Pass `--pid <n>` to every later call (`send`, `key`, `read`, `shot`, `record`, `close`); other sessions may have coach windows open in parallel, and a call without the pid is refused rather than guessed. Then `just wez record --pid <n> run.gif --send "<the command you changed>" --seconds <long enough for the run>`.
2. Read `run-sheet-1.png` (and later sheets): every fourth frame of the run on one page. Then read single frames from `run-frames/` at full size wherever a row, a picture, or a spinner looks off. A bug that only shows while a call runs (a row drawn twice, a picture in the wrong place, a spinner that sticks) never shows in a final screenshot.
3. `just wez close --pid <n>`, your window only. Report what the frames showed: "rung 5, frames 40 to 80: one working row, grid under the items row".

Text-only changes may stop at rungs 1 to 4; pictures, layout, motion, and anything ConPTY could reorder (cursor moves, escape sequences) need rung 5. Charts and icons draw only in terminals with images (WezTerm, Kitty, Ghostty, iTerm2); the desktop app's terminal pane, Windows Terminal, and tui-test show the text fallback (block-character strips), which is that fallback working, not a bug. Sixel is opt-in via `PI_FORCE_IMAGE_PROTOCOL=sixel` (never auto-enabled from a terminal identity variable).
